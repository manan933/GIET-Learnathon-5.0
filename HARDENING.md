# Security Hardening Register — HostelGrievance

| ID | Finding | Risk | Change | Verification | Residual Risk |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **H-01** | **Broken Object-Level Authorization (IDOR/BOLA) on Grievance Access (`GET /api/grievances/:id`)** | High / Confidentiality breach: Any authenticated student could view any other student's grievance details by simply modifying the ID parameter in the URL. | Enforced `assertCanViewGrievance(user, row)` server-side in `src/server/routes/grievances.ts`. Rejects unauthorized cross-tenant requests with `403 Forbidden`. | Vitest test case `student cannot access another student’s grievance` verifies that student `stu-1` is blocked with HTTP 403 when requesting `GRV-0003` belonging to `stu-2`. | User ID spoofing remains impossible as identity is derived strictly from server-validated session cookie. |
| **H-02** | **Broken Object-Level Authorization (IDOR) on Grievance Comments (`GET` / `POST /api/grievances/:id/comments`)** | High / Integrity & Privacy: Any student could view private comments and post unauthorized comments on other students' grievances without ownership checks. | Added `assertCanViewGrievance(user, row)` validation on both GET and POST comment routes, ensuring only the grievance owner or wardens can read or contribute comments. | Vitest test case `student cannot view or post comments on another student’s grievance` confirms HTTP 403 on comment read and write attempts against cross-account tickets. | Wardens can participate across all grievances by design to fulfill their administrative responsibilities. |
| **H-03** | **Unauthorized Grievance Tampering & Parameter Tampering (`PATCH /api/grievances/:id`)** | Critical / Integrity: Students could edit titles, descriptions, and categories of other students' grievances, and students could alter ticket statuses. | Added strict student ownership validation (`row.student_id === user.id`), prevented students from altering status (`403 Forbidden`), and blocked edits to resolved grievances (`409 Conflict`). Wardens are restricted to status updates only. | Vitest test cases `status changes work for wardens and are forbidden for students` and `lets a student edit their own open grievance but not a resolved one or other student’s` confirm proper role separation. | Status updates by wardens are logged for administrative auditability. |
| **H-04** | **Broken Object-Level Authorization (IDOR) on File Attachments (`GET /api/attachments/:id`)** | High / Data Leakage: Students could download photo attachments belonging to other students' private grievances by knowing or enumerating attachment IDs. | Added `assertCanViewGrievance(user, grievanceRow)` authorization check in `src/server/routes/attachments.ts` prior to serving attachment bytes. | Vitest test case `attachment metadata, magic byte check, and storage work with IDOR authorization` confirms HTTP 403 when `priya@example.test` attempts to download `att-5` belonging to `stu-1`. | Legitimate grievance owners and wardens retain authorized access. |
| **H-05** | **Stored Cross-Site Scripting (XSS) in Comment Timeline (`{@html comment.body}`)** | High / Client Compromise: The frontend renders comment bodies via Svelte `{@html comment.body}`, allowing attackers to execute arbitrary JavaScript in the browsers of viewing students or wardens. | Implemented server-side HTML entity sanitization (`sanitizeText`) in `src/server/security/sanitize.ts` and applied it to comment bodies, grievance titles, and descriptions upon storage and response. | Vitest test `comments work for permitted users and sanitize HTML against XSS` verifies that `<script>alert("XSS")</script>` is encoded as `&lt;script&gt;` and neutralizes script execution. | Non-HTML formatting such as newlines is preserved safely using CSS `whitespace-pre-line`. |
| **H-06** | **Unsalted Password Hashing (`sha256:hash`)** | Medium / Offline Cracking: Passwords were saved using fast, unsalted single-iteration SHA-256, vulnerable to rainbow tables and GPU brute-force. | Upgraded password hashing in `src/server/auth/passwords.ts` to `scrypt` with a cryptographically secure 16-byte random salt and 64-byte key length (`scrypt:salt:hash`), while maintaining backward compatibility for legacy hashes. | Tested via Vitest auth tests and verified seeded database accounts (`student123`, `warden123`) generate and verify salted scrypt hashes. | Passwords in transit must be protected by HTTPS/TLS in production. |
| **H-07** | **Indefinite Session Validity & Missing Expiration Check** | High / Session Hijacking: `readSessionUser` queried `expires_at` but never validated it against the current timestamp, meaning sessions remained active forever. | Added expiration timestamp comparison `new Date(row.expires_at).getTime() <= Date.now()`, automatically pruning expired sessions and returning unauthenticated status. | Verified in session unit tests that expired session tokens are pruned and rejected with HTTP 401. | Active sessions remain valid until `SESSION_TTL_SECONDS` (7 days) expires or user logs out. |
| **H-08** | **Session Invalidation Failure on Logout** | Medium / Token Reuse: `POST /api/logout` cleared the browser cookie but failed to delete the active session token from the SQLite `sessions` table. | Updated `POST /api/logout` to explicitly execute `destroySession(db, token)` against SQLite, ensuring tokens cannot be replayed even if retained by client. | Vitest test `current-user works after login and session is destroyed in DB after logout` verifies that using the same session token after logout returns HTTP 401. | Users must ensure their browser cookies are not physically stolen on shared workstations. |
| **H-09** | **Insecure Session Cookie Flags** | Medium / Cookie Interception: Session cookies were issued without `HttpOnly`, `SameSite`, or `Secure` attributes, exposing them to XSS theft and CSRF. | Updated `setSessionCookie` in `src/server/auth/session.ts` to set `httpOnly: true`, `sameSite: 'Lax'`, `path: '/'`, and `secure: isProd`. | Verified `Set-Cookie` header attributes in API responses. | `Secure` flag activates automatically in production environments (`NODE_ENV=production`). |
| **H-10** | **Unsafe Upload Storage Filename & Path Traversal Risk** | High / Arbitrary File Overwrite: `newStoredName` accepted client-supplied `originalName` as the stored disk filename, creating path traversal (`../`) and file overwrite risks. | Modified `newStoredName` in `src/server/storage/attachments.ts` to ALWAYS generate a random 16-byte hex filename (`<randomHex>.<ext>`) and completely ignore client-supplied paths on disk. | Vitest file upload tests confirm disk files use randomized hex names inside isolated `uploads/` directory. | Metadata preserves cleaned original filename for display without exposing filesystem paths. |
| **H-11** | **Missing Magic-Byte / File Signature Validation for Uploads** | High / Malicious File Upload: Attachments were checked only against client-declared MIME type headers, allowing attackers to upload shell scripts or executables disguised as images. | Implemented `validateImageSignature` in `src/server/storage/attachments.ts` checking binary headers for JPEG (`FF D8 FF`), PNG (`89 50 4E 47`), GIF (`GIF87a`/`GIF89a`), and WebP (`RIFF...WEBP`). | Vitest test `rejects oversized, disallowed, or spoofed attachments` verifies that a shell script spoofed as `image/png` is rejected with HTTP 400. | Polyglot files are mitigated by strict content-type headers, non-executable filesystem storage, and isolated sandbox headers. |
| **H-12** | **Overly Permissive CORS Configuration with Credentials** | High / Cross-Origin Attacks: CORS was configured as `origin: (origin) => origin ?? '*', credentials: true`, reflecting arbitrary origins while transmitting credentials. | Restricted CORS in `src/server/app.ts` to an explicit allowlist of trusted origins (`http://localhost:5173`, `http://127.0.0.1:5173`, etc.) with strict allowed methods and headers. | Tested cross-origin requests; untrusted origins receive no CORS authorization headers. | Wildcard access is completely prevented when credentials are enabled. |
| **H-13** | **Internal Error Information Leakage** | Low / Info Disclosure: `handleError` returned raw `err.message` in HTTP 500 JSON responses, leaking database syntax, table names, and internal stack traces. | Updated `handleError` in `src/server/http/errors.ts` to log errors server-side only and return a generic `{ error: "Internal server error.", code: "internal" }` to clients. | Vitest test `returns 404 for unknown grievance ids without leaking internals` and 500 error tests confirm zero leakage of `sqlite`, `ENOENT`, or stack traces. | Diagnostic information is safely retained in protected server console logs. |
| **H-14** | **Missing HTTP Security Headers & Missing Anti-Sniff Protection** | Medium / Clickjacking & MIME Confusion: Application responses lacked standard security headers, and attachment downloads lacked content-type isolation. | Added global middleware setting `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Content-Security-Policy: default-src 'none'; sandbox` on file downloads. | Verified response headers on API and attachment endpoints. | Compatible with all existing frozen frontend components. |
| **H-15** | **Lack of Security Event Visibility & Audit Logging** | Medium / Forensics & Detection: Security-critical actions (login attempts, access denials, rate-limit hits, file uploads) were not tracked for incident response. | Created `src/server/security/audit.ts` emitting structured `[SECURITY AUDIT]` logs with timestamps, event types, user IDs, roles, IP addresses, and resource contexts (without sensitive credentials). | Test outputs show structured audit log entries for all authentication, access denial, and upload events. | Logs must be aggregated and monitored by the host system's centralized logging pipeline. |
| **H-16** | **Authentication & Resource Abuse via Brute-Force** | Medium / Availability & Brute-Force: Login and grievance/comment creation had no rate limits, permitting automated credential stuffing and resource exhaustion. | Implemented sliding-window rate limiting (`src/server/security/rate-limit.ts`) capping login attempts (10/min) and grievance/comment filings per user. | Tested rate limit enforcement returning HTTP 429 when thresholds are exceeded. | In distributed multi-instance deployments, a shared Redis or SQLite rate-limiting table can be used. |
